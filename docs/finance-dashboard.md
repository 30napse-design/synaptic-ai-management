# Financial dashboard — page 01

## Source and boundaries
The approved page-01 brief is implemented on `/finance/dashboard`, on top of published v54 `1829c09eeb79ca2d826a1ae5b88cfe3b4fd5d6b9`. Existing reception, laboratory center, intake, custody, QC, finance ledgers and all original documents remain canonical. No schema migration, live account/permission update or operational import is needed or performed.

`lib/finance-dashboard.ts` projects existing financial documents, verified transactions, payables, structured accepted-contract installments, tax records, petty-review rows, permitted decisions, mother projects, jobs and shared dispatch tickets. It does not write invoice/contract amounts, bank entries, scientific decisions or settlement. The dashboard's only ordinary mutations are audited follow-ups and reminder settings; monetary actions remain in the existing financial writer. Contract installment reviews are actions rather than an invented unpaid accounting balance; petty review dates are not misrepresented as contractual due dates.

## Financial correctness
- Display unit: toman; canonical transaction amounts stay rial. Gross verified receipts, verified outgoing payment/expense/refund and net cash are period-specific. Issued-invoice receivables are a current ledger balance, not a historic snapshot.
- Reported, void or unmatched bank entries never count as confirmed proceeds. Verified refunds reduce invoice allocations; installments allocate verified net receipts oldest-first and keep partial balances open.
- Unknown/no verified period data and absent invoice ledgers return null rather than fake zeros. No prior receivables snapshot means no growth percentage for that measure. Zero previous cash denominator is not reported as an infinite percentage. Financial data completeness across all real bank accounts is not established.
- Month buckets use Persian-calendar boundaries. Custom dates are validated, capped at two years and compared with an equally long previous period. The monthly/weekly/daily Persian calendar derives from the source records; it stores no duplicate installments.
- Unmatched mother projects remain searchable and explicitly labelled incomplete; declared invoice/slip amounts are not included in receivables or cash KPI totals.
- Laboratory workflow state and verified settlement do not themselves grant scientific or delivery approval. Existing final-release gates remain authoritative. The settled status card explicitly requires checking actual delivery permission.

## Authorization and shared tickets
Only the primary Owner or explicit finance-data permission can read the dashboard. Technical institute administration alone does not grant financial access or approval. Approval is separately checked server-side. The UI derives Owner, finance approver and non-approving finance-permission views from existing grants; no new organizational role or real appointment is created. A dedicated Financial Specialist role remains an organizational decision because the existing nine roles contain no such role.

`/api/internal-tickets` is a permission-checked adapter over the existing dispatch engine, `ops_items`, `ops_communications`, role tasks, events and work-file storage. It reuses the nine central role definitions and their active appointments. The same UI is used by the financial dashboard and the existing employee cartable. It supports incoming/outgoing/waiting/forwarded/archive views, filters, replies, forwarding, internal unit notes, attachments and history. Server identity determines sender; callers cannot impersonate another unit. Existing self-assignment rules remain enforced. Missing role owners go to management review. A ticket request for a formal invoice creates no legal/tax issuance.

Participants and source permissions govern ticket/text/file access; communication-specific draft ACLs and unit-internal note visibility also apply in the legacy dispatch/operations readers. Forwarding keeps the previous participants/history and creates the existing role-specific task rather than a parallel ticket. Calendar follow-up tasks require finance permission when opened or listed after a role change.

## Reminders and independent operation
Settings/history use existing `finance_settings`/`finance_events`; default reminders are 7/3/0 days and daily after overdue. Source-backed event IDs, due date and day determine stable notification IDs. Existing ticket tasks are reused. Settlement is recomputed from confirmed allocations; just viewing, following up or completing an ordinary task never settles money. Insertion guards check source revision and the current verified outstanding balance. Payment changes can therefore prevent a stale reminder write.

The financial sweep is wired into the existing authenticated `/api/integrations/tick`, after the existing source/follow-up pipeline. There is no second scheduler. An authorized finance approver may explicitly run today's sweep from the dashboard. No production cron, secret or external service is activated. A token being configured is not proof of a running scheduler; the dashboard says so. Actual independent reminders require the Owner's approved host scheduler to call the existing endpoint with `SYNAPSE_AUTOMATION_TOKEN`, plus observation of a successful scheduled run. Keep that token in host Secrets, never Git or chat.

## Navigation and remaining product dependencies
- Invoice/document search opens the existing precise document with `?id=`; mother search opens its existing project. The dedicated page 02 has not yet been designed/implemented. No placeholder page or duplicate financial case store is created.
- Transaction and bank views, evidence, quote/contracts, payables, petty cash, tariffs, tax/formal invoice and reports keep their existing routes. Receipt shortcuts open the real reported-receipt form and do not approve bank funds. CSV upload/import and its existing duplicate checks remain available. Excel `.xlsx` first-sheet import uses the read-only `read-excel-file` adapter and the same validated CSV/bank import path; it supports the explicit rial template and Persian/Gregorian dates, with a one-megabyte file and 5,000-row preview limit. It does not execute workbook formulas, convert currencies implicitly or post money on file selection.
- Role/contract financial approval ceilings and final managerial authority follow existing policy; the dashboard does not invent new thresholds or an approval bypass. Advanced accounting-system mismatch detection, actual-profitability reconciliation and every future page-08 subflow are not claimed complete.
- No supported browser-control/secure production employee session was available in this environment. Synthetic API/SSR results do not certify desktop/mobile visual acceptance, real employee login, real cron execution, external delivery or a complete D1/R2 recovery.

## Verification

Existing finance lifecycle and laboratory-center suites provide regression coverage. All data, sessions, files and approvals in those tests are isolated synthetic fixtures.
