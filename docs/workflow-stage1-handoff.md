## تغییرات

1. وصول وجه فقط از خالص دریافت منهای استرداد تأییدشده در `finance_transactions` محاسبه می‌شود. پرچم قدیمی `ops_items.payment_state=verified`، اعلام مشتری و مبالغ دستی آزمایشگاه مجوز وصول یا اجرا نیستند. ارقام تاریخی در بخش سوابق مالی غیرقطعی محفوظ‌اند.
2. اتصال صریح ورودی به سند از API مالی موجود، با `action: link_operation`، `id: documentId` و `operation_id` انجام می‌شود؛ فقط تأییدکننده مالیِ مجاز به همان ورودی می‌تواند آن را ثبت کند. اتصال با `finance_links` موجود، ثبت تاریخچه و بدون تطبیق حدسی نام/تلفن است. اتصال به سند متفاوت یا مبهم نیازمند تطبیق مدیریتی است. رابط تطبیق گروهی سوابق قدیمی ساخته نشده است.
3. مرجع مالی اجرای آزمایشگاه در writer مشترک قرار گرفت. مسیر مالی، `job_save` و API قدیمی برای ایجاد سفارش باید شناسه فاکتور صادرشده و شناسه ردیف معتبر داشته باشند. شرح، مقدار، مشتری و مرجع از سند مالی خوانده می‌شوند؛ هر ردیف همان نسخه فقط یک سفارش دارد.
4. کنترل مالی در SQL نوشتن و batch اتمیک دوباره اعمال می‌شود؛ پذیرش، پیشرفت و ثبت نتیجه نیز مجوز جاری را بررسی می‌کنند. ابطال سند یا افت وصول بر اثر استرداد، اجازه ادامه ثبت اجرا را نمی‌دهد؛ توقف کار همچنان ممکن است. آزمایشگاه تأیید مالی انسانیِ مجدد انجام نمی‌دهد.
5. دسترسی داده عملیات: مجوز دسته + مسئول یا ثبت‌کننده همان رکورد؛ مدیریت دسترسی مدیریتی موجود را حفظ می‌کند. حساب آزمایشگاه به API عملیات عمومی دسترسی ندارد. فهرست، جزئیات، جست‌وجو، تاریخچه، شمارش و رویدادها همگی محدودند. نام همکاران مجاز برای ارجاع همچنان در دسترس است.
6. رکوردهای کارتابل/پروژه علاوه بر مجوز ماژول، مسئول، بازبین یا همکار ثبت‌شده می‌خواهند. مسیر علمی نیز برای ورودی عملیاتی از همان کنترل استفاده می‌کند. تغییر منو مجوز داده ایجاد نمی‌کند؛ حساب‌ها و مجوزهای ذخیره‌شده کارکنان تغییر نکردند.
7. تأیید دستی وصول در رابط عملیات غیرفعال و مسیر مالی قدیمی مدیریت به دفتر مالی اصلی هدایت شد. صدور از فرم قدیمی بدون مرجع معتبر مسدود است؛ مسیر عملیاتی موجود برای صدور جدید، ردیف فاکتور در بخش مالی است.

## بررسی واقعی

- `npm run build`: موفق.
- `node node_modules/typescript/bin/tsc --noEmit --incremental false`: موفق.
- شش فایل تست سیاست مالی، آزمایشگاه، مجوز، عملیات، ارجاع و ناوبری: موفق.
- `node scripts/test-finance-runtime.mjs finance-runtime.mjs workflow-stage1-runtime.mjs`: موفق؛ گردش مالی قبلی و ۹۷ بررسی HTTP مرحله اول، به‌اضافه assertionهای داده.
- موارد بررسی‌شده: ناشناس و غیرمجاز، پرونده دیگران و حساب آزمایشگاه، وصول جعلی/تأییدنشده، پرداخت جزئی زیر/برابر حداقل، سفارش چندخدمتی، مسیر قدیمی، ثبت هم‌زمان تکراری، استرداد، ابطال سند، لغو مجوز و حداقل صفر.
- همه تست‌های runtime در Miniflare با D1/R2 موقت و داده ساختگی اجرا شدند. SQLهای schema صرفاً برای ساخت محیط خالی تست استفاده شدند؛ Migration و دیتابیس زنده اجرا/تغییر نکردند.
- فایل‌های سربرگ، shell، تنظیمات حساب، احراز هویت حساب‌ها، CSS تأییدشده و schema تغییر نکردند. تغییر `staff-server` فقط نگهداری مجوز داده جدا از مجوز نمایش منو است.

## موارد مسدود و تصمیم لازم

- سفارش‌ها/درخواست‌های قدیمی بدون اتصال معتبر به سند مالی، خودکار معتبر نمی‌شوند. اجرای آن‌ها تا تطبیق و اتصال مصوب مسدود است؛ هیچ تبدیل یا اتصال روی داده زنده انجام نشده است.
- سیاست مصوب فعلی `execution_min=0` حفظ شده: فاکتور صادرشده با حداقل صفر، اعتبار بدون پیش‌پرداخت محسوب می‌شود. اجباری‌کردن پیش‌پرداخت برای همه، تصمیم مالی جدید است.
- صف مشترک بررسی و انتساب براساس سمت/جانشین سازمانی، موضوع مرحله بعد است. در این مرحله دسترسی کارکنان به پرونده خودشان محدود و پرونده‌های واردشده بدون مسئول برای مدیریت قابل مشاهده‌اند.
- فرم‌های قدیمی فاقد مرجع مالی راه دورزدن ندارند؛ بازفعال‌کردن آن‌ها یا تطبیق سفارش تاریخی با سند، نیازمند تصمیم درباره گردش اصلاح/تطبیق است.
- بدون Migration، وابستگی یا سرویس جدید؛ در انتقال هاست، خاصیت اتمیک batch و کنترل مالی داخل SQL باید حفظ شود. این تغییر به‌تنهایی استقلال اتصال‌های Sites یا انتقال هویت را فراهم نمی‌کند.

## اعمال پس از تأیید

Commit همین شاخه را در محیط بررسی روی آخرین شاخه Work cherry-pick کنید و اختلاف احتمالی را همان‌جا حل کنید. سپس Build و تست مرتبط را با داده آزمایشی اجرا کنید. هیچ merge به main، انتشار یا اعمال داده در این تحویل انجام نشده است.
