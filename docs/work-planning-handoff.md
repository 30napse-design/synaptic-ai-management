# تحویل اصلاح زیرسیستم کار و برنامه‌ریزی SYNAPSE

## مبنا و محدوده

- مبنا: `cc1d5caa7aace1481d6d7ceb60a0fe64a83c9c6d`، نسخه منتشرشده ۳۳.
- آخرین `origin/main` هنگام شروع با مبنا یکسان بود؛ تغییر تازه‌ای برای ادغام وجود نداشت.
- شاخه مستقل محلی: `work/my-planning`. هیچ push، انتشار، Migration عملیاتی یا تغییر secret انجام نشده است.

## پیاده‌سازی

پنج گزینه منوی کار: امروز من، همه وظایف، برد وظایف، برنامه‌ریزی، بررسی و تأیید. داشبورد مدیریتی مستقل قبلی در گروه مدیریت باقی است. مسیرهای قبلی فاکتور، ریسلر، افراد و لینک مستقیم سایر انواع رکورد به رابط قبلی هدایت می‌شوند.

`lib/work-policy.ts` مرجع مشترک محاسبه خانه شخصی و کارتابل است. امروز بر مبنای مسئول یا همکار واقعی و تاریخ اجرا یا موعد امروز است. زمان ایجاد نقشی ندارد. عقب‌افتاده‌ها در همه وظایف باقی می‌مانند. پروژه و فاکتور مستقل به عنوان وظیفه نمایش داده نمی‌شوند؛ وظایف علمی اجرایی قبلی حفظ می‌شوند.

- همه وظایف: دامنه شخصی/همه مجاز، عقب‌افتاده، امروز، آینده، بدون تاریخ، اجرا، انتظار، تکمیل؛ فیلتر ترکیبی مسئول، همکار، واحد، پروژه، اولویت، تاریخ، وضعیت و جستجو.
- برد: شش وضعیت، تب ستون در موبایل، اسکرول داخلی دسکتاپ، هشدار موعد مستقل از وضعیت. رهاکردن کارت جزئیات مقصد را باز می‌کند و ثبت انتقال با همان مجوز و گزارش انجام می‌شود.
- تقویم: روزانه، هفته از شنبه و ماه کامل شمسی. تاریخ اجرا مستقل از مهلت، ساعت شروع/پایان، یادآوری داخل سامانه. برنامه‌ریزی یک وظیفه موجود از ویرایش همان رکورد انجام می‌شود؛ نسخه مستقلی ساخته نمی‌شود.
- تأیید: منتظر من، ارسال‌شده توسط من، تاریخچه تصمیم‌ها؛ تأیید، دلیل اصلاح و درخواست اطلاعات. مدیر می‌تواند تأییدکننده دیگری انتخاب یا تأیید اجباری را برای کار غیرفعال کند.
- جزئیات: مسئول پاسخ‌گو، همکاران، پیشرفت، زیرکار/چک‌لیست، پیوست واقعی R2، گفتگو، منشن انتخابی با `@`، همکاری، تاریخچه و ارجاع به موجودیت‌ها.
- اعلان: یک زنگ بالای صفحه، گیرنده مجاز، خوانده‌شدن ماندگار، شناسه یکتا برای جلوگیری از تکرار و یادآوری جدا برای هر کاربر.
- همگام‌سازی: دریافت کارتابل هر ۲۰ ثانیه، اعلان‌ها هر ۳۰ ثانیه، دریافت مجدد هنگام بازگشت به پنجره و دکمه دستی. Revision فرم باز ثابت است؛ تغییر هم‌زمان متن را خودکار بازنویسی نمی‌کند و ثبت نسخه قدیمی 409 می‌دهد.
- اجازه ایجاد و ارجاع همچنان با مدیریت است؛ کارکنان می‌توانند گزارش، گفتگو و همکاری روی کار مجاز ثبت کنند. قاعده منع خودارجاع و مجوزهای مستقل مالی/علمی حفظ شده‌اند.

## مدل داده، نگاشت و سازگاری

Migration `drizzle/0017_work_planning.sql` فقط سه جدول و دو index اضافه می‌کند؛ هیچ رکورد موجود تبدیل، حذف یا با شناسه جدید کپی نمی‌شود:

| ذخیره | کاربرد |
|---|---|
| `staff_records` | همان شناسه، متن، مسئول، موعد و Revision قبلی |
| `staff_work_details` | یک رکورد به ازای همان شناسه: تاریخ/ساعت اجرا، همکاران، پیشرفت، زیرکار، الزام تأیید، ارجاع و یادآوری |
| `staff_events` | همان تاریخچه قبلی به همراه تصمیم‌ها، گزارش‌ها و جزئیات قبل/بعد ویرایش |
| `staff_work_files` | فراداده پیوست با همان شناسه وظیفه؛ فایل در R2 با پیشوند `work/` |
| `staff_work_notifications` | اعلان گیرنده و وضعیت خوانده‌شدن |

رکورد قدیمی بدون فراداده، تاریخ اجرای آن از `due` خوانده می‌شود؛ تأیید پیش‌فرض الزامی است. پیوندهای پروژه/سفارش/مشتری/فاکتور، نوع و شناسه مرجع و لینک منبع‌اند؛ داده موجودیت‌های دیگر تغییر نمی‌کند و همگام‌سازی خارجی انجام نمی‌شود.

خواندن رکوردها در دسته‌های ۵۰۰تایی است؛ محدودیت حذف‌کننده ۱۰۰۰ برداشته شد. صفحه در دسته‌های ۵۰تایی نمایش می‌دهد. این نسخه هنوز snapshot کامل مجاز را به مرورگر می‌فرستد؛ صفحه‌بندی شبکه‌ای مستقل و SSE/WebSocket ندارد. برای حجم‌های بسیار بزرگ باید endpoint صفحه‌بندی شبکه‌ای و دریافت تغییرات افزوده شود.

## آزمون و شواهد

نتایج نهایی در `docs/work-planning-verification.txt` ثبت می‌شوند. همه داده‌های آزمون مصنوعی صرفاً در D1/R2 حافظه‌ای Miniflare بوده‌اند؛ تست‌ها نشانی زنده ندارند.

| سناریو | روش بررسی |
|---|---|
| ارجاع برای سه روز آینده و ورود در روز مقرر | آزمون سیاست تاریخ با روز قابل تزریق و API ایجاد/تغییر برنامه |
| شروع کار و انعکاس وضعیت | API واقعی Worker و دریافت مجدد همان رکورد |
| باقی‌ماندن موعدگذشته خارج از امروز | آزمون مشترک خلاصه و فیلتر |
| پیام/منشن و اعلان همکار | API واقعی، خواندن اعلان و ثبت خوانده‌شدن |
| ارسال برای تأیید فرد مجاز | API واقعی با حساب مستقل reviewer و آزمون یکسانی خلاصه |
| بازگشت برای اصلاح و حفظ دلیل | API واقعی و خواندن تاریخچه |
| داده مجاز در موبایل و دسکتاپ | رندر HTML با دو User-Agent و کنترل دسترسی API؛ آزمون تعاملی بصری انجام نشده |
| حفظ پروژه و داده عملیاتی | مقایسه قبل/بعد رکورد پروژه در آزمون محلی؛ هیچ عملیات زنده انجام نشده |

همچنین بیش از ۱۰۰۰ رکورد، Revision قدیمی و دو درخواست هم‌زمان، پیوست واقعی/دریافت مجاز/رد فرد نامرتبط، مسیر قدیمی API، تکمیل بدون تأیید اجباری، تقویم شمسی و تغییر تاریخ بدون ایجاد رکورد دوم بررسی شده‌اند.

- صحت رفتاری سایت زنده با حساب‌های عملیاتی آزمایش نشده؛ نسخه زنده عمداً دست‌نخورده است.

## اعمال و انتشار پس از تأیید مدیر

1. در محیط جداگانه، ZIP سورس را باز کنید یا شاخه تحویل را از bundle وارد کنید. پیش از ادغام، `main` را دوباره دریافت و اختلاف‌های جدید را حفظ کنید.
2. `pnpm install --frozen-lockfile` و سپس `pnpm exec tsc --noEmit`، آزمون‌ها و `pnpm build` را اجرا کنید.
3. در پایگاه‌داده آزمایشی، Migration شماره ۱۷ را **پس از Migration شماره ۱۶** با runner فعلی پروژه اعمال کنید. DB و BUCKET موجود کافی‌اند؛ secret جدید لازم نیست. Snapshot شماره ۱۷ و journal همراه سورس هستند. این تغییر را به‌صورت SQL جدید از قبلِ snapshot تولید مجدد نکنید.
4. آزمون مرورگر در سه عرض، تغییر تاریخ، درگ برد، بازکردن اعلان، آپلود و دو کاربر هم‌زمان را کامل کنید. وضعیت فعلی کاندید انتشار است و این مرحله هنوز باقی است.
5. پس از تأیید نهایی، از D1 و فایل‌های R2 نسخه پشتیبان بگیرید؛ Migration را در پنجره کنترل‌شده و پیش از فعال‌کردن کد جدید اعمال کنید. ادغام و انتشار را با روند موجود Sites انجام دهید؛ project_id، مخاطبان، DB/BUCKET و secrets را حفظ کنید.

دستور آزمون‌های منطقی:

```sh
node --input-type=module -e "import fs from 'node:fs'; for (const f of fs.readdirSync('tests').filter(f=>f.endsWith('.test.mjs'))) await import('./tests/'+f)"
node scripts/test-work-planning-runtime.mjs
```

## بازگشت

ابتدا نوشتن را موقتاً متوقف و از وضعیت جاری پشتیبان بگیرید. برای بازگشت صرف کد، جدول‌های افزوده و فایل‌های R2 را حذف نکنید؛ شناسه‌ها و فراداده محفوظ می‌مانند. تنها وضعیت جدید `changes` در UI نسخه ۳۳ شناخته نیست: آداپتور اختیاری `drizzle/rollback/0017_work_planning_compat.sql` نگاشت آن به `doing` را با نگهداری مقدار و Revision قبلی انجام می‌دهد. SQL بازگرداندن فقط ردیف‌های دست‌نخورده نیز در همان فایل آمده است؛ موارد تغییرکرده باید دستی تطبیق داده شوند. این آداپتور اجرا نشده است. بازگردانی کامل backup تنها با تصمیم مالک و تطبیق تغییرات پس از استقرار انجام شود.
