# مرجع مرکزی سورس SYNAPSE و هماهنگی Work / Codex

## مرجع و نسخه مبنا

مخزن اصلی متصل به Sites:

`https://git.chatgpt-team.site/827182ab-5c0a-49f4-a427-68ec851cd5ac/appgprj_6af06be01a5481918c6578c73c9b888a.git`

شاخه مشترک فعلی `main` است. مبنا باید از آخرین Git مشترک یا تحویل رسمی Work تعیین شود؛ نام ZIP، تاریخ فایل و آخرین خروجی محلی به‌تنهایی مرجع نیستند. دریافت آخرین source با احراز هویت کوتاه‌مدت Sites انجام می‌شود؛ token فقط در حافظه/ورودی مخفی، نه URL، فایل، log یا آرشیو.

پیش از کدنویسی:

1. وضعیت محلی و شاخه‌های منتشرنشده را حفظ کنید. `git status`، remote و SHAهای کامل را ثبت کنید.
2. source مشترک را fetch کنید؛ credential منقضی را از Sites تمدید کنید. اگر Git قابل دریافت نبود، فقط bundle رسمی Work با provenance و commit معتبر قابل قبول است. این محدودیت را اعلام کنید؛ ZIP قدیمی را جایگزین آخرین Work نکنید.
3. با `get_site`، `list_site_versions` و وضعیت deployment مربوط، نسخه ذخیره‌شده را از نسخه واقعاً منتشرشده جدا کنید. آخرین نسخه ذخیره‌شده الزاماً live نیست.
4. SHA مشترک، SHA منتشرشده، شاخه توسعه و شواهد تأیید مالک را جدا ثبت کنید. تأیید صریح مالک را از موفقیت Build یا انتشار استنتاج نکنید.
5. اگر نسخه‌ها متفاوت‌اند، علت/اختلاف فایل‌ها و ancestry را بررسی کنید. اگر Work جلو رفته، تغییرات آن باید در مبنا حفظ شوند. شاخه قبلی را reset یا حذف نکنید. اختلاف‌های واقعی را روی شاخه مستقل ادغام و بررسی کنید؛ از force-push یا کپی کامل پوشه قدیمی روی Work جدید خودداری کنید.
6. شاخه مستقل `work/<موضوع-کوتاه>` یا `codex/<موضوع-کوتاه>` از مبنای منتخب بسازید. از tracking تصادفی main روی شاخه تحویل اجتناب کنید. نوشتن روی main، push، انتشار یا Migration زنده عملیات جدا هستند و صرف بسته‌بندی آن‌ها را مجاز نمی‌کند.

در این نوبت، shared source و انتشار موفق نسخه ۳۶ هر دو commit `8f13eb3dd5ff3db4df54b3c4666771750faca273` بودند. شاخه `work/source-governance` از همان commit ساخته شد. اصلاحات تاریخ و خانهٔ Work حفظ شدند. commit محلی `b4e1d79` هنوز روی شاخه قبلی محفوظ است؛ SHA آن به‌تنهایی مبنای نسخه ۳۶ نیست، زیرا Work تغییرات را با commitهای خودش وارد کرده است.

## ثبت وضعیت نسخه‌ها

`observed-2026-11-12.json` ثبت تاریخیِ زمان بررسی است، نه ادعای «همیشه آخرین». در هر مأموریت تازه Git و Sites را دوباره بخوانید و یک observation جدید با نام `observed-YYYY-MM-DD[-موضوع].json` ثبت کنید. نسخه live، آخرین shared commit، تحویل‌های محلی و وضعیت تأیید را مخلوط نکنید.

تحویل همین شاخه، «آماده بررسی/آرشیوشده» است و جایگزین خودکار نسخه تأییدشده محصول یا نسخه live نمی‌شود. commit نهایی دقیق داخل manifest خروجی تولید می‌شود تا سند commit خودش را پیش‌بینی نکند.

## ساخت بسته استاندارد

پس از commit، با working tree تمیز:

```sh
python3 scripts/release/package.py \
  --base <SHA-کامل-مبنای-تأییدشده> \
  --work-ref origin/main \
  --provenance docs/source-control/observed-2026-11-12.json \
  --out /workspace/exports/<پوشه-جدید-برای-این-تحویل>
```

اسکریپت فقط Git محلی را می‌خواند و فایل خروجی می‌سازد؛ fetch/push/deploy/Migration انجام نمی‌دهد. مسئول توسعه باید پیش از اجرای آن واقعاً fetch و provenance را تازه کرده باشد. اسکریپت مانع بسته‌بندی شاخه‌ای می‌شود که از shared ref ثبت‌شده مشتق نیست، یا روی main است، یا تغییرات commit‌نشده دارد. اگر آخرین Work روی شاخه رسمی متفاوت است، `--work-ref` و provenance را مطابق شواهد واقعی تنظیم کنید.

هر پوشه خروجی شامل:

- `SYNAPSE-source.zip`: کل درخت tracked همان commit، با ساختار اصلی؛ بدون node_modules، credential و state محیط اجرا.
- `SYNAPSE-changes.patch`: patch باینری نسبت به SHA پایه؛ base صریح و قابل بررسی.
- `SYNAPSE-full.bundle`: تاریخچه کامل reachable شاخه‌ها و tagهای محلی، شامل شاخه تحویل؛ بدون پیش‌نیاز برای بازیابی مستقل.
- `manifest.json`: SHA کامل‌ها، وضعیت مشاهده‌شده، نام شاخه، فایل‌های تغییرکرده، checksum و دامنه آرشیو.
- `SHA256SUMS`، `APPLY-AND-RESTORE-FA.md` و `SYNAPSE-release.zip` برای دریافت یکجا.

بسته ZIP سورس با blobهای Git مقایسه می‌شود، bundle verify می‌شود و patch از سمت نسخه نهایی reverse-check می‌شود. در تحویل مرجع، بازیابی bundle در یک مخزن موقت مستقل هم بررسی می‌شود. این آزمون داده عملیاتی را لمس نمی‌کند.

## آرشیو Google Drive

حساب مقصد: **AI Manager — `30napse@gmail.com`**. پیش از هر upload، هویت فعلی connector را با `get_profile` تأیید کنید؛ label یا link_id قدیمی کافی نیست.

پوشه موجود و خصوصی:

`https://drive.google.com/drive/folders/1Uzl3YvidLofmL4zbsd-mowHY58DnfyKx`

برای هر تحویل یک زیرپوشه تازه با الگوی `YYYY-MM-DD_<شاخه-کوتاه>_<SHA12>` ایجاد کنید. نام‌ها را به جای فایل‌های قدیمی overwrite نکنید؛ sharing را تغییر ندهید. سورس، patch، bundle، manifest و راهنما را در همان زیرپوشه نگه دارید. بعد از upload با metadata خواندن مجدد، نام، اندازه، parent و URL را تأیید کنید.

اتصال مجاز به Drive، مجوز عمومی‌کردن سورس نیست. اگر upload یا مجوز حساب واقعاً مسدود شد، آرشیو محلی را سالم نگه دارید، محدودیت مشخص را گزارش کنید و ادعای موفقیت نکنید. حساب مقصد را بدون دستور مالک عوض نکنید.

## ساختار مستندات

- `docs/source-control/`: انتخاب مرجع، observationها و استاندارد نسخه‌ها.
- `docs/deployment/`: وابستگی‌ها، انتقال و برنامه بازیابی روی زیرساخت مستقل.
- `docs/*-handoff.md`: راهنماهای موجود ماژول‌ها؛ مسیرشان برای حفظ لینک‌های قدیمی تغییر نکرده است.
- `scripts/release/`: ابزار ساخت تحویل؛ خروجی‌ها بیرون Git یا در مسیر ignored قرار می‌گیرند.
- `tests/release/`: آزمون ساخت و بازیابی بسته، بدون داده زنده.

## مرز پشتیبان‌گیری

سورس و Git bundle برای بازیابی **کد و تاریخچه** هستند. D1 عملیاتی، فایل‌های R2، secrets، اتصال‌های OAuth، DNS و دسترسی دامنه داخل آن‌ها نیستند. backup و انتقال این موارد نیازمند مأموریت جداگانه و مجوز مالک است. مستندات مسیر انتقال را روشن می‌کنند؛ به معنی اجرای انتقال نیستند.

برای پیدا کردن آخرین تحویل بدون اتکا به نام ZIP، فایل `SYNAPSE-LATEST.json`
در ریشه آرشیو به زیرپوشه آخرین تحویل اشاره می‌کند. این pointer بین «آخرین
shared/live مشاهده‌شده» و «آخرین تحویل بررسی‌نشده» تمایز می‌گذارد؛ commit
آرشیوشده را خودکار تأییدشده یا منتشرشده تلقی نکنید. خود نسخه‌های قدیمی تغییر
نمی‌کنند. پس از هر upload، pointer تنها پس از خواندن مجدد فایل‌های مقصد به‌روز شود.
